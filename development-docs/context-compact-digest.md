# 上下文压缩方案：主题 Digest + 批次发号归档

Status: **已由 [`context-compact-summary.md`](context-compact-summary.md) 取代**（2026-08-31 一条概要 + 尾部原文）。下文为历史归档带 / L1–L3 设计。  
**时间分层（原文带 / 整合带 / 归档带）与归档带改意** 见 [`context-compact-time-bands.md`](context-compact-time-bands.md)。当前测试期工作上下文以归档 Digest 投影为准（L1 为发现用索引，见 time-bands §2.3）。  
§12–§16、工作模型内置系统前缀仍以本文为 v1 实现说明。  
组批、锁定、预压缩、工具去细节化物理层仍以 [`context-compact-turn-archive.md`](context-compact-turn-archive.md) 为准。

## 0. 要解决的问题

当前达阈后，工作模型看到的是按时间排列的多份批次摘要（`summary_batches` JSON）。实测反馈包括：

- 跨批重复抄写稳定事实（参数表、任务列表），浪费预算；
- 进行中状态没有时间或终态，过期快照被当成现行事实；
- 跑题段落占满整批摘要，与当前主题无关。

根因不是「写单批的模型完全没读 prior」，而是 **旧批次摘要落库后不再改写**，投影把每一批全文并排送给工作模型。时间线归档与「现行世界观」被做成了同一份东西。

固定每 **B** 轮切批（默认 8）是暴力的，不按语义。v1 **不**用模型切批（边界不稳、多一次长窗口调用、和预压/锁定难对齐）。主题脉络交给 Digest 跨批缝合；批次只负责发号和归档。

---

## 1. 原则

1. **仓库按时间切块发号；读模型按主题看现行状态。**
2. **工作上下文默认只放一份会改写的 Digest**。不把各批长摘要当第二份正文，也不把仅含 id 的 `notes` 清单发给工作模型。
3. **一切细节库 id 由程序发放。** 模型只准抄提示里出现过的号；程序做闭集校验。禁止模型编 UUID。
4. **「有过这件事」写在 Digest 正文**，不靠几个字的 hint。hint 可以没有。
5. 下钻用已有 `query_detail_store(detail_id)`：`detail_id` 为 `batchId`（整批原文）或工具 `detail_ref` 上的 id。
6. 批次大小 **B 是上限**（可设置），不是语义章节。人工语义边界继续用**锁定**。

---

## 2. 三层（存储 / 流水线，不是每轮平铺给模型）

| 层 | 名称 | 谁写 | 谁读 | 变不变 |
|----|------|------|------|--------|
| L1 | **Digest**（主题现行摘要） | Digest 模型 + 程序拼装 JSON | **工作模型主读物** | 每批正式落库后改写；有长度上限 |
| L2 | **批次短摘要** + `batchId` | 批次总结模型 | **主要给 Digest 作者当输入**；工作上下文默认不放全文 | 落库后只读 |
| L3 | **细节库原文** | 程序（整批原文、工具载荷） | `query_detail_store` | 按 id 查 |

工具去细节化仍是发送路径上的另一套 L3（`detail_id` ≈ `toolCallId`），与 `batchId` 键空间不同；批总结式压缩落库后回收该批内工具级细节，规则不变（见归档文档 §0、§3.6）。

**刻意不做：** 工作模型每轮同时读长 Digest + 长 `summary_batches` 正文（会再重复一遍现行事实）。

## 3. 工作上下文投影

### 3.1 达阈前

与归档文档 §9 相同：内置机制前缀 + 用户系统提示 + 活跃记忆 + 历史（工具可 `detail_ref`）+ 当前轮 live 全文。无 Digest。

### 3.2 达阈后（有可用 Digest）

```
[内置系统前缀：机制说明已改为 Digest 语义]
+ [用户系统提示]
+ [活跃记忆块]
+ [技能目录（若开启）]
+ 一条合成消息 context_digest_*（见 §3.3）
+ 锁定轮：原文（总结式压缩不生效；工具可去细节化）
+ 尾部最近 B 轮：原文
+ 当前轮 live：工具全文
```

不投影各批摘要正文。工作模型从 Digest 正文知道「有哪些事」；需要下钻时只抄 digest 里出现过的 `batchId`，或消息里 `detail_ref` 的 `detail_id`。

### 3.3 `context_digest` 载荷

```json
{
  "type": "context_digest",
  "rev": 7,
  "digest": "<主题概括 Markdown；现行事实以本文为准>"
}
```

- **不**把 `notes`（批次 id 清单）发给工作模型。裸 id 没有 L2 摘要，抄号也帮不上忙。
- `digest`：Digest 模型输出。引用细节时**整段抄写**提示里闭集的完整 `batchId`（写 Digest 时那份 `batchId → 短摘要`）。推荐行内用反引号包住完整号。禁止截断或省略号。
- `rev`：每次成功更新 +1，便于调试与忽略过期投影。
- **导出**（给人看，不进工作 JSON）：按原文路径重建 `notes`: `{id, summary, origin}`，以便对照 L1 是根据哪些 L2 来的。

「查看上下文」：Digest 给人读（可读化只渲染 digest 正文）。批次原文仍按 `batchId` 在细节库。

### 3.4 Fallback（无 Digest 或更新失败且从未成功过）

退回今日行为：投影 `summary_batches` JSON（各批摘要全文 + `batchId`）。有上一份成功 Digest 时，更新失败则**沿用旧 Digest**，不撕掉工作模型的现行世界观。

## 4. 批次层（发号与归档）

组批、锁定切割、预压满 B、不满批仅正式压、输入必须为会话原文（禁止以 `detail_ref` 为总结输入）、落库后 `batchId` 进细节库：均同归档文档 §2–§5。

**v1 不引入模型语义切批。** 若将来做，只能是「在 ≤2B 轮缓冲里提议切点」，且每块必须落在 `[Bmin, B]`，非法则退回固定 B。

### 4.1 批次短摘要的职责（相对现状要收紧）

读者是 **Digest 模型**，不是工作模型。目标是短目录项：本批新增/变更、未决、本批出现过的主题（多主题就并列，不要拧成一个故事）。不要完整背景、不要复述更早批次或用户 Wiki。

`batchId` 由程序贴在块外，批次模型**不要**编 id。

**批次总结输入不再带更早批次短摘要。** 跨批整合只在 L1（§13）。归档文档旧 §4.5 已作废。

### 4.2 脚注粒度

v1：**一个 `batchId` 对应整批原文**（实现已如此）。一批多主题时，一次下钻会拉回整批——可接受。Digest 正文负责点出各主题并挂上该批 `batchId`；落库前程序要求闭集每个号至少出现一次。

若以后不可接受：在细节库按 `turnId` 建索引或支持 `batchId` 内按轮切片，Digest 改引轮级 id。非 v1 必做。

## 5. Digest 生命周期

Digest 跟**对话分支**走（分叉时拷贝）。建议持久化在对话/分支上：`digestJson` + `digestRev`（或等价合成消息，投影器插入 retain 窗口之前）。

### 5.1 增量（正式压缩：新批 `attach` 成功之后）

一次 LLM 调用，输入：

1. 旧 Digest 正文（可空）；
2. 闭集：`batchId → 该批短摘要`（含刚落库的本批）；
3. 可选但推荐：本批**原文**（与 `formatBatchOriginals` 同形），避免只靠短摘要丢细节再写入 Digest。

输出：新 `digest` 字符串。程序：

- 扫描引用的 id ⊆ 本次闭集；非法引用删除后若正文非空则落库。漏抄不拦截。测试期：漏抄、剥了非法号、写失败、结束后仍无 Digest，都弹必须确认的对话框；不靠 Snackbar 或只打日志。
- 拼 `notes`（程序列表，不采用模型输出的 notes）；
- `rev++` 落库。

Digest 作者**可以**只读当前全局活跃记忆与用户自定义人设（§15），用于辨名、避免写出和用户知识相反的句子；**禁止**把 Wiki 整段抄进 Digest，也**禁止**挂 `query_detail_store`。对话原文与旧 Digest 优先于这份背景。

### 5.2 预压缩

只写该批短摘要并归档原文。**不**每次预压都改 Digest。正式达阈（或本轮正式压缩收尾）再更新 Digest，避免界面与上下文抖动。

### 5.3 全量重压（用户可见：全量重新压缩）

丢掉已有批次摘要，按原文重新组批并逐批总结（每批**只看本批原文**，不带更早 L2）。全部批成功后，用「全部短摘要 + 空或旧 Digest + 当前用户注入知识」重建 Digest。不要每批都对全量原文再跑一遍 Digest。

这与 §16 的「更新会话摘要」不是同一件事：后者**不**清批次、**不**重写 L2。

### 5.4 预算

Digest 正文设目标上限（实现时选一个，例如约 2k–4k token 或固定字数）。提示词要求超限则合并主题、覆盖过时条。Digest 必须是滚动覆盖，不能只追加。

批次总结、Digest、整合请求必须显式带 `maxTokens`：压缩模型自己的 `maxTokens`，否则全局 `defaultMaxTokens`，都没有则用高级设置滑条上限 32768。不要省略该字段（提供方会落到很小的默认输出上限，Digest 会在 `stop_reason=length` 时空正文）。不要发送提供方最大输出（例如 384K）。

### 5.5 与锁定、尾部原文

Digest 只概括**已入总结式压缩批次**的前缀。锁定轮与尾部 B 轮仍以消息原文为准；系统前缀写明这一点，避免 Digest 假装覆盖未压内容。

## 6. 内置提示词（两套 + 系统前缀）

用户**不可编辑**总结式压缩提示词（与归档文档一致）。两套系统提示职责不得混用。

### 6.1 批次短摘要

相对现 `BuiltInPrompts.CONTEXT_COMPACT_SYSTEM` 再收：

- **只根据本批原文写**；不要附带更早批次短摘要、不要附带活跃记忆/默认提示词、不要挂 `query_detail_store`；
- 短；多主题并列；进度带时间或写成终态；
- 不要「对全部对话的总结」、不要补会话外背景；不要编 id；
- 语言随对话，只输出本批摘要。

### 6.2 Digest

单独提示，大意：

- 维护一份发现用归档索引，不是按 batch 编年复述，也不是把各批中间稿粘成设计说明书；
- 覆盖过时数字；跑题收成一句并挂对应完整 `batchId`；
- 下钻处从闭集**整段**抄写 id，禁止自造、截断、省略号；闭集每个 `batchId` 必须在正文至少完整出现一次，拿不准归属也要挂完整号；程序不补全截断号；
- 若提示里带有用户活跃记忆/人设：只作背景，不要整段搬进正文；与原文冲突时原文和旧 Digest 优先；
- 结构随对话变，不要写死工程六段表；
- 遵守长度上限；
- 只输出 digest 正文（或约定 JSON 的 `digest` 字段）。
- 不要调用工具。

### 6.3 工作模型系统前缀（内置，非用户 Default）

发给**工作模型**的 SYSTEM 固定为：

`[Agora 机制前缀] + [用户编译后的系统提示] + [活跃记忆块] + [技能目录]`

机制前缀由 `AgoraSystemPrefix` 在 `GenerationRequestBuilder.buildEffectiveSystemPrompt` **编译时注入**，不是设置里可编辑的 Default。用户换成自定义短提示也会带上。上下文详情里的 SYSTEM 与线上一致，会先出现这段。正文为中文；JSON 字段名（`context_digest`、`batchId`、`detail_ref` 等）保持英文。

正文要点：

- 本块是 Agora 运行时政策，不是用户人设；
- 先读 `type=context_digest`；**已压缩前缀的现行事实以 digest 为准**；
- 查库：只抄 digest 正文中的 `batchId`，或消息里 `detail_ref` 的 `detail_id`；禁止猜测 id；
- 锁定轮与尾部 B 轮仍是原文，Digest 不覆盖它们；
- 覆盖顺序见 §14：live / 尾部原文 / 锁定轮 → Digest → 用户注入的活跃记忆与默认提示词；
- `summary_batches` 仅出现在 fallback。

旧安装若把 `Context compression (Agora):` 写进了用户 Default：启动时 `migrateBakedAgoraPolicyFromPrompt` 剥掉，避免编辑器里还能改、发送时双份。不要把机制说明写回 `DefaultSystemPrompt`。

Digest 作者**不要**收这份前缀，也不要收工厂 Default（含 `You are a helpful assistant in Agora.` 及工具说明书）；只收用户自定义人设（见 §9 非目标与 §10 第 8 条）。

不要 bump `CompactFormat.CURRENT_REV`：只改工作模型看到的系统说明，不改编排/摘要输入。

## 7. 谁填写「见 batchId」

**Digest 模型填写**，不是程序做语义对齐。

程序在提示里给出闭集（id + 该批短摘要，增量可加本批原文）。模型同时看见内容和合法号，必须整段抄完整 `batchId`。程序只删闭集外的完整号，不根据前缀补全截断号。漏抄仍落库，测试期弹强制确认对话框报告缺号。

v1 不要求 hint；不要求程序把句子挂钩到某一批。

## 8. 失败与兼容

| 情况 | 行为 |
|------|------|
| 批次总结失败 | 不入批、不更新 Digest（同现网） |
| Digest 失败且曾成功 | 沿用旧 Digest；测试期强制弹窗 |
| Digest 从未成功 | Fallback `summary_batches`；测试期强制弹窗 |
| Digest 已落库但漏抄 / 剥了非法号 | 仍用这份 Digest；测试期强制弹窗 |
| 导出 | digest 正文 + 各批 `summary` + `origin`（origin 仍为 stub 前原文）；工作 JSON 无 `notes` |

不改变：失败工具不去细节化；压缩不删除会话 UI/Room 原文；不满批不预压。

## 9. 非目标（本文增量）

- 用 LLM 按语义切批作为 v1。
- 工作上下文并排长 Digest 与长批次摘要正文。
- 模型生成 `batchId` / `detail_id`。
- 程序 NLP 给句子贴脚注。
- 把某套工程文档结构写死进引擎。
- v1 必须上轮级细节 id。
- 用 Digest 替代锁定或尾部原文。
- 给批次/Digest 模型挂 `query_detail_store` 或整份 Agora 默认系统提示（含 shell/记忆工具政策）。
- 会话内由模型改写活跃记忆原文（`update_active_memory`）。
- 已保存记忆（`memory_db` 文件库）作为模型知识体系的一部分。
- 改全局记忆/提示词时立刻对所有会话跑压缩；或做成可跳过仍发送的「暂不」。

归档文档 §10 的非目标仍然有效。

## 10. 建议实现顺序

已完成（v1 + §12–§16）：

1. 持久化 Digest；投影有 Digest 走 §3.2，否则 `summary_batches`。
2. 写 Digest 时程序给闭集（id + 短摘要）并校验抄号；工作模型 JSON 不带 `notes`。
3. 正式 `attach` 后更新 Digest；预压不改 Digest。
4. 工作模型系统前缀改为编译时注入（`AgoraSystemPrefix`），从用户 Default 剥离。
5. 批次总结去掉更早 L2 prior（§13）。
6. 删除已保存记忆整套；去掉 `update_active_memory`（§15）。
7. 全局知识 rev + 发送前「更新会话摘要」拦截（§16）。
8. Digest 调用只读用户注入知识（活跃记忆 + 用户自定义提示中的稳定人设），不要整份 Agora 工具说明书，也不要内置机制前缀。

相关代码：`SummaryBatchProjection.kt`、`ContextDigest.kt`、`BatchCompactEngine.kt`、`BuiltInPrompts.kt`、`AgoraSystemPrefix.kt`、`DefaultSystemPrompt.kt`、`MemoryManager.kt`、`DigestKnowledge.kt`、`DigestSendPrompt.kt`、`AutomaticCompactSendPrompt.kt`。

## 13. 批次总结不再带更早 L2

v1 实现里，写第 N 批时会把更早批次短摘要当作 prior 塞进 User（归档文档旧 §4.5）。那是给**工作模型并排读长 L2** 时用的消歧手段。

L1 上线后，跨批整合、覆盖过时事实、去重都在 Digest。L2 只是 Digest 的原子原料。再给每批总结带上全部更早 L2：

- 与 Digest 输入（旧 Digest + 闭集全部短摘要）重复；
- 税落在**更勤**的预压缩路径上，且随批次数线性变长，没有硬顶。

**改为：** 批次 LLM 只收压缩系统提示 + 本批原文（工具结果仍为全文、不做 `detail_ref`）。不要 prior、不要用户默认提示词、不要工具。Digest 增量仍收：旧 Digest + 闭集全部 `batchId → 短摘要` + 本批原文 + §15 的只读用户知识。

## 14. 权威顺序（同一类事实只认一层）

会话模型会同时看见：**内置机制前缀**、用户系统提示、活跃记忆、Digest、尾部原文。必须写死，避免两套真理：

1. **本轮 live、尾部 B 轮原文、锁定轮**（刚发生的、未进总结式压缩的）
2. **会话摘要（Digest）**（已压缩前缀的现行状态）
3. **活跃记忆 + 默认提示词里用户注入的知识**（跨会话底稿）

记忆/提示词与 Digest 打架时，**本会话以 Digest 和原文为准**。底稿只解释专有名词、补 Digest 没提的身份偏好；不要用底稿另造一套架构。

项目过程中会变的决定应出现在**对话原文**里，从而进入 L2 → Digest。不要把同一事实既写进活跃记忆又写进 Digest 当双权威。

## 15. 记忆系统改造

### 15.1 现状（改造前）

- **活跃记忆**：全局文件 `active_memory.md`。每次发送现场读入 `{active_memory}`。模型可 `update_active_memory`（replace/append/prepend/patch）；设置页也可改。所有会话共享、随时可变。压缩路径**不读**它。
- **默认提示词**：会话只存 `systemPromptId`，指向全局库。改库后所有绑该 id 的旧会话下一轮立刻用新正文，不重压、不更新 Digest。
- **已保存记忆**：`memory_db/*.md` + 描述。不自动进上下文。模型 list/read/create/edit/delete。更像资料库，但模型会把它当第二套世界状态。

结果：工作模型每轮读**最新**全局 Wiki，Digest 只根据聊天记录写，两边对不上；一场会话改记忆还会污染其他会话。

### 15.2 活跃记忆

定位改为：**完全由用户维护的业务知识注入渠道**，与默认提示词同类——进每场会话 SYSTEM 里用户提示词一侧（`<active_memory_context>`），会话内只读。内置机制前缀是另一层，不承载用户 Wiki。

- **删除** `update_active_memory`（及对应工具定义）。模型不得改原文。
- 用户只在设置里改全局底稿。没有「本会话一份可编辑拷贝」的入口。
- 会话进行期间底稿对模型冻结；用户改全局之后走 §16，而不是静默换开头。

### 15.3 默认提示词

同样是全局、用户改。改的是提示词库里的条目。绑该 id 且**已经有会话摘要**的对话，在下次发送前按 §16 更新 L1。新建会话直接用新正文，无需压缩。

提示词适合放稳定行为（语言、语气、禁区）。可变项目 Wiki 放活跃记忆，不要把记忆职责塞进提示词变成垃圾桶。

### 15.4 已保存记忆：整套删除

不改名、不留成「本地文档」。理由：

- 「当外部文档、非用户点名不读」靠提示词压不住；有 list/read/create 就会变成 Digest 之外的知识层；
- 本机已有文件读写工具；再做一套 app 内 md 库是重复的私人 Wiki；
- 与细节库职责不同（细节库是本会话被投影摘掉的原文），但会和 Digest 抢「事实放哪」。

删除范围：`MemoryToolProvider` 里 list/read/create/edit/delete、`memory_db`、设置页文件列表、相关开关。跨会话手册用用户自己的文件；始终在场的一小段只用活跃记忆/默认提示词。若以后要「把某次聊天落盘」，做成用户显式导出，不要做成模型默认可写的知识层。

### 15.5 不按会话做可编辑快照

知识是全局的，用户也只在全局改。不需要会话级可修改人设。对齐靠 **rev 比较 + 惰性更新 L1**（§16），不是每场拷一份正文再让用户改拷贝。

## 16. 更新会话摘要（仅重建 L1）

### 16.1 和全量重新压缩的区别

| | 全量重新压缩 | 更新会话摘要 |
|--|--|--|
| 批次摘要 | 全部丢掉重写 | **不动** |
| 会话摘要 | 全部批成功后再写 | **只**重写这一份 |
| 何时 | 压缩/投影契约变了（`compactFormatRev` 落后）；用户明确点全量；旧胶囊迁移 | 全局活跃记忆/所用提示词相对本会话上次写 Digest 时已变，且本会话**已有成功 Digest** |
| 费用 | 与历史长度成正比 | 一次 Digest 调用 |

没有 Digest 的会话（含一直走 `summary_batches` 回退）：换开头知识即可，**不必**压、也不必弹「更新会话摘要」。L2 不携带用户 Wiki，原料仍合法。残留风险：回退路径上新 Wiki 与旧批次长摘要并排，用户把 Wiki 改成和当年聊天相反时只能靠模型判断——可接受。

有 Digest 时，**用户知识变化**不要走 `fullRecompact` 清批次。**上下文机制变化**（应用常量 `CompactFormat.CURRENT_REV`）要走全量。

### 16.1.1 压缩契约版本

会话表 `compactFormatRev`：0 = 版本化之前写成的压缩。应用常量 `CompactFormat.CURRENT_REV`（机制变了才加一，改活跃记忆/提示词不加）。

发送时若路径上已有批次、Digest 或旧胶囊，且 `compactFormatRev < CURRENT_REV` → **必须全量重新压缩**才能发送（弹窗文案单独写，不能跳过）。全量成功（含没有可写批次、只卸旧胶囊）后把会话 rev 写成当前值。没有压缩痕迹的对话不弹。任务/循环静默全量，失败则本轮不发。增量压缩或预压缩若会话上**已有**压缩痕迹，不要把 rev 写成当前值，否则旧批次会被当成新契约。

升级后所有旧压缩会话下次发送都会拦一次；不要在设置保存时扫全库开压。

### 16.2 惰性：发送时判断，不改全局就全库开压

设置里改活跃记忆或提示词时，**不要**扫所有会话立刻压缩。

建议存版本号，而不是给每个会话打标：

- 全局：`activeMemoryRev`；提示词条目自己的 `rev`
- 会话：上次成功写成 Digest 时用过的那两个 rev（或合成 `digestBackgroundRev`），以及当时的 `systemPromptId`

发送路径：若本会话**有可用 Digest**，且（`digestBackgroundRev` 落后于全局，或 `systemPromptId` 已换）→ **先拦截，再弹窗**，不要带着新 Wiki + 旧 Digest 发出去。

未打开的旧会话磁盘上仍是旧 Digest，直到下次在该会话发送。

「查看上下文」若不发送：按同一条件决定是否也重建；默认可与发送一致，避免预览当权威时新旧并排。

### 16.3 发送拦截弹窗

形态接近已有「发送前压缩上下文？」（`AutomaticCompactSendPrompt`），**语义相反**：

- 已有达阈弹窗的「暂不压缩」= **仍发送**（`SendWithoutCompact`）。
- 本弹窗：**不更新就不能发送**。

按钮：

- 主：**更新并发送** — 重建会话摘要成功后再走原发送（若同时还超自动压缩阈，可先更新 L1 再走达阈压缩，或合成一步，避免连弹两次）。
- 次：**暂不发送** — `AbortSend`：不发送、不改 Digest；草稿保留；下次发送再弹。

不要复用「暂不压缩」文案。不要提供「跳过更新仍发送」。不要在设置里放手动「更新会话摘要」。

失败：沿用旧 Digest，本轮不发送（或明确报错），以免新 Wiki 配旧摘要出门。

### 16.4 Digest 调用输入（本操作）

与 §5.1 相同形状，但：

- 闭集 = 路径上已有全部批次短摘要（不重写它们）；
- 本批原文可空（没有新 attach）；
- 带上**当前**全局活跃记忆与所用提示词中的用户人设；
- 旧 Digest 可作「改写起点」，但必须按新背景覆盖过时条。
